# IGP24 Stage-0 Notes

## Axplorer Architecture

Axplorer exposes each math search task as an environment under `src/envs/`. The
registry in `src/envs/__init__.py` maps `--env_name` strings to environment
classes. `train.py` parses global flags, calls the selected environment's
`register_args`, builds the environment, generates initial `DataPoint` objects,
tokenizes them, trains a decoder-only model, samples new token sequences,
detokenizes them, scores them, optionally runs local search, and keeps the best
population.

The important extension points are:

- `DataPoint`: owns object construction, `calc_features`, `calc_score`, and
  bounded `local_search`.
- `BaseEnvironment`: configures task-level class parameters and exposes a
  tokenizer.
- `Tokenizer`: maps task objects to/from integer sequences for the transformer.
- `src/datasets.py`: calls `DataPoint._batch_generate_and_score(batch_size, N)`
  and deduplicates by `features`.

The `igp24` environment plugs into this flow with `IGP24DataPoint` and a custom
fixed-length signed-coefficient tokenizer. `train.py` still passes `args.N`, so
the environment registers `--N` with default `24` and rejects other values, but
the leading coefficient is never generated by the model.

## Why Axplorer Here

IGP24 asks for monic degree-24 integer polynomials with useful
Galois-group/signature pairs and preferably small discriminants. Axplorer is a
good stage-0 candidate generator because its loop already supports:

- random initial generation,
- deterministic scoring,
- model sampling over tokenized objects,
- local repair/improvement,
- population selection and deduplication.

For this phase, Axplorer is not an exact verifier. It is a generator and proxy
ranker that can produce plausible candidates for later PARI, MAGMA, or SAIR
verification.

## Proxy Scoring

Exact `24Tt` labels require external Galois group verification. Stage 0 does not
fake them. The scorer rejects invalid candidates using exact algebraic checks
available through SymPy, then ranks valid candidates by:

- optional target real-root-count match,
- smaller `log(abs(discriminant))`,
- smaller coefficient height,
- diversity of modular factorization degree patterns at small unramified
  primes,
- novelty relative to canonical translation hashes.

The modular factorization data is only Frobenius cycle-type proxy evidence. It
can guide search, but it does not determine or certify the exact Galois group.

Stage-1 scoring records a component breakdown in candidate metadata. The score
still has no exact group-label component; `target_t` remains metadata only. The
breakdown is meant to explain whether a candidate ranked well because of root
count match, novelty, modular pattern diversity, small height, or small
discriminant proxy.

## Stage-1 Generation

The IGP24 environment now supports several initial generation strategies:

- `uniform`: dense coefficients sampled from the full search box.
- `low_height`: dense coefficients sampled from a smaller inner box.
- `sparse`: a configurable number of nonzero free coefficients.
- `lower_degree`: coefficients biased toward lower-degree terms.
- `structured`: simple sparse binomial/trinomial-like seeds.
- `four_real_seed`: an experimental `target_r=4`-oriented seed that starts
  near `(x^2-a)(x^2-b)(x^20+1)` and adds small odd perturbations.
- `mixed`: a weighted mix of the above.

These are still candidate-generation heuristics, not structured Galois-family
certificates. Their job is to produce a more varied stream for exact SymPy
prefilters, proxy scoring, and later external verification.

The stage-1 benchmark helper runs short CPU-only `train.py` generation jobs and
summarizes JSONL ledger records. IGP24 now seeds NumPy from `--seed` during
environment setup so process-pool-off generation benchmarks are reproducible.

A short benchmark with seeds `101,102`, `coeff_bound=4`, `gensize=12`, and
`max_local_search_steps=3` found that `structured` and `sparse` were the
strongest small-sample strategies: `structured` had the best average mean score
and fastest high-scoring runs, while `sparse` found the best single candidate.
Uniform generation was slowest and lowest-scoring. As a conservative default,
the `mixed` strategy now weights sparse and structured generation more heavily
than uniform generation, while keeping all strategies active:

```text
uniform:0.10,low_height:0.20,sparse:0.25,lower_degree:0.20,structured:0.25
```

This weighting is a stage-1 heuristic only. It should be revisited after larger
benchmarks and, later, exact external verification.

The benchmark helper also supports target real-root-count comparisons through
`--target_rs`. A short run over `sparse`, `structured`, and `mixed` with
untargeted scoring and `target_r=2` showed:

- `sparse` had the highest `r=2` match rate in this small sample,
- `structured` kept the strongest untargeted average score,
- target-r scoring mostly shifted scores by the intended real-root-count bonus,
- no generation default should be retuned from this tiny target-r run alone.

The target-r data is useful for reporting and experiment planning, but it is
still proxy scoring. It does not imply any exact `24Tt` label.

A larger CPU-only target-r comparison with seeds `301,302,303,304`,
`gensize=18`, `pop_size=8`, and targets `none,0,2,4` sharpened the stage-1
picture without changing that caveat. `structured` looked strongest for
`target_r=0`, with the best average best score, average mean score, and match
rate among the tested strategies. `sparse` remained the most reliable way to
hit `target_r=2`, while `structured` produced better `r=2` peak and average
best scores. Current families are weak for `target_r=4`: `mixed` and `sparse`
found some matching records, but match rates stayed low, and `structured`
almost never hit the target. Untargeted scoring still favored `structured` on
average score.

This argues against a single global default retune. The next useful step is
target-specific presets or run recommendations, plus new `r=4`-friendlier
families before trying to tune `mixed` weights for that target.

The first `r=4`-friendlier family is `four_real_seed`. It is intentionally
explicit rather than part of the default `mixed` distribution: it biases the
candidate stream toward a polynomial shape with four real roots, then perturbs
odd coefficients so the generator is not merely emitting the reducible even
product. In a bounded CPU-only comparison against `sparse` and `mixed` with
seeds `401,402,403,404`, `four_real_seed` improved average `target_r=4` match
rate to 0.792, versus 0.200 for `mixed` and 0.164 for `sparse`. It also
improved average mean score, but `sparse` still found the best single candidate
score in that batch. Treat this as evidence that the family is useful for
target-yield, not as proof that it is best for final candidate quality.

## Why Random Polynomials Are Limited

Random degree-24 integer polynomials often land in generic, unstructured cases.
That can still be useful for exercising the pipeline and finding small
discriminants, but many competition targets likely require more structured
families. Real-root counts, discriminants, and small-prime factorization patterns
are useful cheap signals because they are related to signature, arithmetic
complexity, and possible cycle types, but they are not a substitute for exact
verification.

## Future Structured Families

Later stages should add targeted candidate families such as:

- sparse polynomials,
- compositional and tower constructions with degrees multiplying to 24,
- resolvent-inspired families,
- solvable or imprimitive group families,
- group-specific modular cycle-type filters,
- discriminant minimization and refinement loops.

## Environment Setup

The project environment is defined in `environment.yml`. SymPy is required for
the exact polynomial utilities. GPU and PyTorch installation details can be
machine-specific; avoid hard-coding CUDA assumptions in project code.
